# Portable MTF engineering verification — 22 October 2026

Hx15 · engineering contract and requirements/evidence plan v1.

The owner requested pursuit of the entire
`encoder-mtf-portable-training-delivery` Goal after the component audit. This
record bounds the numerical checks needed for that delivery. It authorizes no
scientific score replay, real-data training, trained-model selection, operation
quality study, GPU campaign or application change. Source export is local;
commits, pushes and external publication are outside this request.

## Contract

Question: can another owner construct, update, save/resume and export the
configurable MTF family with the declared learning method and source closure?

Inputs are tiny artificial floating CPU BCHF observations and explicit bool
support, two configured geometries/capacities, explicit source/data/split/recipe
identities, initialization seed, total update budget and AdamW options. Identity
preparation casts to F32, rejects observed nonfinite/overflow and zeros missing
cells; no statistics are fitted. The portable first release is CPU/F32 with one
Torch thread. It preserves the original MTF core, loss arithmetic, masks and
optimizer-then-EMA rule while giving the wrapper/codec/recipe a new identity.

Outputs are raw resumable state, a separate inference-model archive, contextual
online encodings with support masks, parameter inventories and machine-readable
engineering evidence. The complete configured observation window is required;
frequency tokens and global-mean channel mixing establish no prefix-causal or
independent-channel contract. This engineering contract makes no OR-01–OR-13
operation-quality claim and creates no trained application reference.

Continuation is exact only within the named CPU/F32/single-thread build/runtime,
unchanged actual observations/order/support, full configuration, preparation,
sampling/seed protocol, optimizer options, source/split/recipe identities and
fixed total budget. Replacement sampling and full-partition training are
separate portable recipes. Neither is the historical adapter's continuation
protocol merely because its checkpoint can be decoded. Application membership,
authentication, selection and descendant compatibility remain consumer-owned.

## Requirements and checks

1. Use configuration A (C2/H16/F3, latent8, d_model12, one encoder/predictor/
   decoder layer, heads2, scales4/8, strides4/4, bins4) and B (C1/H23/F5,
   latent12, d_model20, depths2/2/1, heads3, scales3/7/31, strides2/4/16,
   bins9). A also uses channel-mask ratio0.10 to exercise channel-target and
   feature-deletion randomness. Use dropout0.1 and nonzero weak-view jitter. F5 observations must
   come from the C++ artificial fixture, not the F3-only historical generator.
2. For each configuration and each of the two portable sampling recipes,
   compare three uninterrupted optimizer updates with one update followed by
   save/load and two updates. Compare all online/teacher parameters, optimizer
   moments/progress and outputs; record actual physical updates, seeds,
   preparation policy, parameter counts and state identities. The expected base
   count is 24 physical updates, plus only explicitly recorded small probes.
3. Verify actual parameter change, nonzero gradients in enabled online branches,
   frozen teacher/no teacher gradients, and the exact post-optimizer EMA rule
   for both teacher encoder and tokenizer. Verify inference export/reload and
   served online state, including global/channel dimensions and validity.
4. Exercise incompatible configuration, preparation, source/data/split/recipe,
   optimizer/runtime/budget and codec refusals. Exercise observed nonfinite,
   F64 overflow, malformed support, missing-only training and legacy/strict
   masking/no-target behavior. Preserve legitimate missing-only inference as
   finite zero invalid output. Confirm full-window/contextual dependency
   semantics through deterministic controlled-input checks, selecting B's
   start0/widthH frequency descriptors for the full-window suffix test, without interpreting
   them as prediction or causal evidence.
5. Run a small native CLI example through fresh preparation/training, partial
   save, resumed completion, inference export/load and embedding extraction.
   Keep its physical updates explicit and bounded. Use raw archives rather
   than application envelopes. Do not run the historical evaluator or the
   large-budget periodic interruption shell fixture.
6. Run exporter integrity/refusal tests and produce a source-only bundle with
   explicit file roles, include closure, SHA256 source/destination mapping,
   notices, training method, limitations and independent offline verification.
   Compile the delivered sources from an isolated bundle root and execute the
   bounded fixture/CLI using only those sources and the existing SDK. Confirm
   compiler dependencies contain the exported source roots, not original
   numerical source. The isolated run has its own actual update count.

## Execution and evidence binding

All builds and checks use the existing `mityane-geometrics` container through
`container.ps1`, root Makefile and `code/scripts/task.sh`. Use at most two
compiler jobs and CPU numerical execution; do not access the GPU. Named build
products stay under `/opt/mityane-geometrics/embeddings/build/hx15-mtf-*`.
Retain run artifacts under
`.temp/embeddings/runs/hx15-mtf-delivery-20261022/attempt-001/` and local exports
under `.temp/embeddings/exports/mtf-family-2026-10-22-001/`.

Before numerical execution, retain a pre-run source/configuration/protocol and
binary identity record in that ignored run directory. A later source repair
requires a distinct attempt/run record and new source identity; preserve failed
logs, artifacts and physical work. The final tracked engineering receipt records
the actual commands, runtime, source/binary/output hashes, physical updates,
pass/failure coverage and limitations. No pass is inferred from fixture source.

The maximum planned primary fixture budget is 48 physical updates per invocation
(24 base updates plus bounded probes); CLI example budget is at most 6 updates.
An isolated-source fixture repeats at most those same 48 updates as a separately
counted portability check. Test failures permit ordinary source fixes and bounded
reruns with preserved attempt identity; they do not authorize a parameter sweep
or quality optimization. Required success is mechanism/continuation correctness,
not loss improvement or downstream utility. SDK/compiler/runtime versions remain
the existing pinned environment; no installation or container lifecycle change
is part of verification.
