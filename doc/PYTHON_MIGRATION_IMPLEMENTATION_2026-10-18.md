# Language migration: complete implementation scope

The owner requested the entire remaining migration in one job and explicitly
allowed Python where it is better suited. This supersedes unconditional
Python-free research execution. The maintained boundary is now:

- Node/Bash for maintenance, input preparation, source capture, receipts,
  metadata summaries, capsule lifecycle and retired-command refusals.
- Python for independent scientific decoding/arithmetic, saved-result audits,
  numerical publishers, TRAIN analysis and their reference/adversarial tests.
- Existing C++ model/operation implementations remain C++. New C++ reader/math
  candidates are optional engineering work, without a certified replacement claim.

The [complete disposition](PYTHON_MIGRATION_DISPOSITION_2026-10-18.json) covers
all 80 baseline Python files, 59 caller files, 161 original command sites and
34 embedded blocks. It records each original hash and the replacement or the
reason Python remains. It is reconciled to the dated
[before-port inventory](PYTHON_MIGRATION_INVENTORY_2026-10-18.json).

Forty baseline files leave maintained Python execution: 30 bookkeeping/reference
files, six retired commands and four previously migrated maintenance tools.
They account for 7,342 physical baseline lines. Forty scientific/reference files
account for 14,017 baseline lines and retain Python for a specific reason. These
are baseline responsibility counts. All 40 replaced `.py` working copies have
now been deleted. Only the 40 declared scientific Python files remain under
maintained `code/` and `web/` source. Mixed modules may retain only a narrow
scientific API or command. The [removal receipt](PYTHON_MIGRATION_REMOVAL_2026-10-18.json)
records every deleted path, replacement and exact archived source identity.

## Implemented maintained paths

All ten input-preparation entry points now have Node implementations and shell
callers. Their source/card/binary closures include the actual Node dependencies.
The two standalone binders retain the closed 195 TRAIN files/15 instances and
85 TRAIN/VALIDATION roles. Explicit immutable recipe configuration replaces
mutable imported Python globals.

The 34 shell heredocs and four SDK proof logging snippets now use named
operations in `code/embeddings/scripts/runner-metadata.mjs`. SDK verification
uses the existing Node verifier, including the three previously stale protocol
calls. No Python interpreter is needed for those metadata operations.

Protocol preparation, source capture and metadata summaries now use family
`.mjs` entry points and shared versioned support. All six retired publication
commands refuse through Node; historical registries remain immutable. Branch,
capacity and relation capsules use Node for their metadata commands. The
capacity capsule retains only its scientific tensor-association `bind` command
in Python, with the complete 18-file observation/witness matrix admitted before
the first decode. The structured-timing Python preparation module retains an
independent contract API used by its scientific reader; its maintained CLI is
Node and the old Python CLI refuses.

The screen/confirmation summaries still depend on completed, hash-bound saved
checks. They do not replace those checks, fit heads, train a model, manufacture
historical inputs or automatically promote an encoder. New JSON receipts name
their encoding and implementation. Metadata means use exact binary rational
accumulation; byte identity with old floating-point JSON/Markdown is not claimed.

## Why the scientific Python remains

Restricted saved-tensor codecs, independent saved CPU mathematics, original
contracts and validators preserve integer behavior, reduction order, thresholds,
failure/abstention semantics and frozen research evidence. Their numerical
publishers perform independent audits even when their filename is `publish.py`.
Replacing this reference code solely to eliminate Python would add substantial
equivalence risk without improving the operation contract.

The retained checks use the managed image's existing Python standard library.
The alternate architecture checker also uses the existing image's PyTorch;
this does not add a package, runtime, container image or model service. Relation
gates remain Python dependencies of the independent numerical publishers. Their
Node counterparts remain separately identified and do not silently replace the
reference used by those auditors.

## Physical paths and preserved identities

Current project execution is rooted at `/mityane`; build products stay under
named `/opt/mityane-geometrics` directories and new selected outputs under
`/mityane/.temp/embeddings/runs`. Maintained scientific path adapters and C++
input/output guards have been updated for these physical locations without
changing scientific arithmetic or existing source/card/reader pins.

For saved parents, `MITYANE_HISTORICAL_PARENT_ROOT` names the explicit component
root **containing** the original `output/runs/...` paths. For imported artifacts
this is `/mityane/code/embeddings`. Node and C++ use the same interpretation;
metadata-only plans keep their original identities and do not require access
to actual parent payloads. The shared C++ mapping header writes a separate
physical-path ledger. The saved-native and amplitude helpers instead require
their exact parent capsule through the corresponding
`*_HISTORICAL_PARENT_CAPSULE` variable.

The codec pin `4eb501222fb1d9205ae13c5bc0bf1b5fc96ebd2faef3ed247dd7809fb86a453d`
continues to identify the original archived codec, located explicitly at
`.archive/embeddings/pre-cleanup-2026-10-18/code/evaluation/protocols/visible_difference_v1/reader-v2/archive_codec.py`.
Consumers no longer try to satisfy that pin with the differently identified
maintained copy. The failed reader-v1 and reader-v2 repair evidence stay
identifiable. New path-adapted readers require their own source fixture/seal;
the historical repair proof does not certify changed bytes.

Replaced Python files are historical source only. Four exact source copies were
already present in the frozen embedding snapshot; 36 distinct maintained-source
versions are preserved under `.archive/python-migration/retired-2026-10-18/`.
Current source closures use the Node replacements and retain Python only where
the scientific implementation actually imports or executes it. Old receipts
and the pre-cleanup snapshot retain their original identities.

Frozen archive bytes, old source capsules, dataset/checkpoint contents and
historical output receipts were not rewritten. The dated inventory preserves
the pre-migration maintained hashes; edited current adapters have new identities.

## Verification boundary

This implementation was initially written and reviewed while the owner required
file edits only. The owner subsequently restored container execution on
18 October. The [validation record](PYTHON_MIGRATION_VERIFICATION_2026-10-18.md)
records the executed engineering checks, repairs and exact source/environment
identities. Earlier source-only records remain dated evidence of that phase.

The root target `test-language-migration` collects Node regression/closure
fixtures, Bash/Node syntax checks, the C++ path-mapping fixture and retained
artificial scientific tests in normal and optimized Python modes. These include
separately identified SOURCE fixtures for the changed scientific reader paths.
It excludes experiment runners, model training and real saved-data audits.
Optional C++ reader/arithmetic candidate tests remain separate. The independent
`test-migration-producer-compile` target compiles the affected producer/reader
translation units with the authoritative Make rules without running them.

Runtime checking found additional old physical paths in C++ protocol programs,
live-source guards and benchmark expectations; they were corrected without
changing recorded historical identities. Make now avoids research provenance
scans for maintenance-only tasks and accepts explicitly supplied actual Git
metadata without redundantly scanning it. Source closures still hash their real
inputs. The engineering acceptance does not certify historical numerical or
serialized-byte equivalence, adopt the optional C++ scientific replacements,
or resume any paused research. The earlier validation record predates working-copy
deletion; [the removal validation](PYTHON_MIGRATION_REMOVAL_2026-10-18.md) records
the checks after deletion. The capacity Python receipt-test module is included
in the original 80-file inventory and has been removed with the other replaced
helpers; its maintained tests use Node.
